## Objective

Establish an operator-controlled Ed25519 release-signing workflow, then use it
to prove signed single-agent deployment and ADB recovery on the qualified Echo
Dot.

## Non-goals

- Placing a release private key in this repository, the gateway, a device, or
  committed test fixtures.
- Implementing the Milestone 4 Gateway Update Manager, release persistence, or
  fleet rollout policy.
- Changing the single-agent installation, launcher, or update protocol already
  implemented by Milestone 3.

## Source references and constraints

- `docs/DESIGN.md` §§10–11: the device verifies a signed manifest before
  atomic replacement; the private key remains in the controlled release
  process.
- `AGENTS.md`: the gateway owns desired state, the Dot owns safe installation,
  and a committed bad agent requires documented ADB recovery.
- Supersedes the live signed-release proof previously described by Milestone 3
  Task 8; its completed disposable offer harness remains the test transport.

## Dependencies and prerequisites

- Milestone 3's `task8gateway`, single-agent installer, launcher, and
  `echoctl update install` implementation.
- A rooted qualified Dot, explicit Linux ADB path and serial, backed-up
  known-good agent/configuration, and a device-lab session.
- An operator-controlled key-management location and a process for injecting
  the matching public key into the test `echod` build without exposing the
  private key.

## Architecture and high-level plan

The signing task produces four operator-held bundle directories: current/newer,
older compatible, immediate-exit diagnostic, and known-good recovery. Each has
an ARM64 artifact, strict manifest, detached signature, and public-key
identifier/material needed to validate it before device deployment. Corrupted
and truncated cases are generated by `task8gateway` response modes; they are
not separately signed artifacts.

The qualification task routes the Dot explicitly to one `task8gateway`
authority, performs each scenario in its own device-lab session, and records
only sanitized evidence. The immediate-exit scenario requires explicit operator
acknowledgement immediately before its offer is sent.

## Numbered tasks

### Task 1: Establish a secure test-release signing workflow

**Status:** not started

**Purpose:** Make valid signed bundles available without weakening the release
trust boundary.

**Dependencies:** operator key-management decision.

**Hardware required:** no.

**Concrete changes:**

- Define a reproducible external or repository-integrated bundle command that
  builds ARM64 `echod`, writes a strict manifest, computes SHA-256, and signs
  the canonical manifest with Ed25519.
- Define secure public-key injection for the corresponding device build and
  an operator-only private-key input that is neither logged nor committed.
- Produce and verify current/newer, older, immediate-exit, and recovery bundles
  with `echoctl release verify` before any device operation.

**Verification:**

```sh
.bin/echoctl release verify --manifest <manifest> --sig <manifest.sig> \
  --pubkey <manifest.pub> --artifact <echod>
```

Expected: every intended bundle verifies with the exact public key embedded in
the qualified `echod` build; no private key enters repository status, logs, or
device storage.

### Task 2: Qualify signed deployment and ADB recovery on the Dot

**Status:** not started

**Purpose:** Prove the installed single-agent boundary with real signed inputs.

**Dependencies:** Task 1 and the completed Milestone 3 offer harness.

**Hardware required:** yes — qualified rooted Dot, prepared device-lab session,
and an explicit operator acknowledgement immediately before the immediate-exit
offer.

**Concrete changes:**

- Prove signed upgrade, restart, reconnect, and matching confirmation.
- Prove signed downgrade as an ordinary deployment.
- Prove truncated, tampered, invalid-signature, and insufficient-space failure
  paths preserve the installed executable digest before rename.
- Offer the immediate-exit signed diagnostic build only after explicit
  acknowledgement; observe launcher backoff and recover by signed ADB install.
- Record downtime, every ADB command, cleanup/verify-clean, and evidence that
  no bootloader, boot, recovery, system, or supervisor path was written.

**Verification:**

```sh
uv run --no-project --script tools/device-lab/device_lab.py preflight \
  --adb "$ADB" --serial "$DEVICE_SERIAL"
uv run --no-project --script tools/device-lab/device_lab.py prepare \
  --adb "$ADB" --serial "$DEVICE_SERIAL" --resume .bin/device-lab/<session-id>
# Run the signed scenarios through task8gateway, recording each installed digest.
uv run --no-project --script tools/device-lab/device_lab.py cleanup \
  --adb "$ADB" --serial "$DEVICE_SERIAL" --resume .bin/device-lab/<session-id>
uv run --no-project --script tools/device-lab/device_lab.py verify-clean \
  --adb "$ADB" --serial "$DEVICE_SERIAL" --resume .bin/device-lab/<session-id>
```

Expected: hardware evidence proves normal signed replacement and downgrade,
pre-commit digest preservation, and manual signed ADB recovery after the
post-commit failure; it never describes this recovery as automatic rollback.
